# Точный перенос — Этап 2: ИИ-дизайн с гарантией дословности

Дата: 2026-07-13
Статус: дизайн утверждён пользователем, ждёт review перед планом реализации
Продолжает: `docs/superpowers/specs/2026-07-08-exact-transfer-design.md` (Этап 1, MVP)

## Связь с Этапом 1

Этап 1 уже реализован: отдельный режим `mode="exact"`, разбор pptx (`parse_pptx`, дословно
+ картинки + диаграммы + заметки), разрез текста по меткам `Слайд N:`
(`parsers/exact_text.py`), детерминированный билдер `pipeline/exact_builder.py`
(`build_exact_plan` → N секций → N `SlidePlan`, `content={"html", "exact": True}`),
ассемблер кладёт контент в `.exact-zone/.exact-fit` (JS ужимает масштаб под 1920×1080),
без ИИ.

**Проблема, ради которой делается Этап 2:** детерминированный билдер сваливает текст в
общие классы (`.exact-text`, `.t-body-30`) без вёрстки — «просто скопировал и вставил в
базовые шаблоны». Пользователь ждёт, что слайд будет **задизайнен и заверстан** в стиле
Cloud.ru (колонки/карточки/иерархия/акценты), но при этом текст останется дословным и
правило 1-в-1 не нарушится.

Этап 1 сам это и запланировал: «Этап 2 (докрутка): апгрейд простых слайдов в нарядные
бренд-шаблоны». Данная спека — его дизайн.

## Цель Этапа 2

Заменить детерминированный дамп на **ИИ-вёрстку** каждого exact-слайда, сохранив ВСЕ
жёсткие гарантии Этапа 1:

- 1 слайд источника → 1 слайд на выходе (не режем, не объединяем);
- текст слово в слово (ничего не сокращаем, не дописываем, не перефразируем);
- сверху — оформление Cloud.ru; логотип/колонтитул/номер добавляет система.

Режим по умолчанию (авто-распределение) не трогаем. Детерминированный билдер Этапа 1
**остаётся** — как страховочный фолбэк (нет ключа к ИИ / сбой / провал проверки).

## Утверждённые решения (из брейншторма 2026-07-13)

1. **Свобода дизайна — «Вёрстка + акценты».** Слова неизменны, но ИИ вправе
   раскладывать их по фирменным раскладкам (колонки, карточки, заголовок из первой
   строки, «Имя — описание» → карточка, крупные числа) И выделять ключевые фразы/числа
   (жирным/крупным). Дословность — на **пословном** уровне: слова сохраняем точно,
   разделительную пунктуацию/буллеты (тире-разделитель, `•`, ведущие номера списка)
   можно «растворить» в вёрстке.
2. **Механизм гарантии — Вариант 2 (структурный): «ИИ выдаёт раскладку, текст
   подставляет программа».** Реализуется как **протокол меток-заполнителей** (ниже):
   ИИ пишет брендовую вёрстку, но на местах текста ставит метки `{{aK}}`, а не сами
   слова. ИИ физически не печатает исходный текст → исказить его не может.
3. **Источник pptx — только текст из XML** (python-pptx, как на Этапе 1). Без
   LibreOffice, без «зрения». 100% дословно, дёшево, быстро.
4. **Границы слайдов в тексте — гибкое авто-распознавание** (СМ. раздел ниже). Это
   **заменяет** строгое правило Этапа 1 «только `Слайд N:`, иначе ошибка».
5. **Экономия токенов заложена** (раздел ниже): кэш-дружелюбная раскладка промпта +
   измерение `usage` + провайдеро-независимые срезы.

## Архитектура и поток данных

Ветка `build_deck(mode="exact")` (`pipeline/build.py::_build_exact`) сейчас:
`parse → build_exact_plan → polish_plan(vision=False, max_autofix=0)`.

Этап 2 вставляет один шаг **между планом и сборкой**:

```
parse → build_exact_plan (детерминир. html = ФОЛБЭК на слайд)
      → design_exact_deck(client, doc, plan)   ← НОВОЕ: ИИ-вёрстка по протоколу меток
      → polish_plan(vision=False, max_autofix=0)  (assemble; ассемблер НЕ меняем)
```

Если клиента/ключа нет или ИИ-шаг для слайда провалился — на слайде остаётся
детерминированный html из `build_exact_plan`. Дека собирается всегда.

### Новый модуль: `pipeline/exact_designer.py`

Содержит: атомизатор, системный промпт, рендер меток, проверки, оркестратор
`design_exact_deck`.

#### 1. Атомизация: `Section → list[Atom]`

`Atom = {id: str, kind: str, text: str}`. Атомы нумеруются `a1..aN` в порядке документа;
заголовок (если есть) — всегда `a1`. Из `Section`:

- `heading` (если непустой) → `a1`, kind `heading`;
- каждый `TextBlock` → один атом kind `paragraph` (внутренние переводы строк сохраняем);
- каждый пункт `ListBlock` → отдельный атом kind `list_item` (общий групповой признак,
  чтобы ИИ мог оставить их списком или разложить по карточкам);
- каждый `TableBlock` → один атом kind `table` (разворачивается программой в брендовую
  таблицу целиком — ИИ её не переставляет по ячейкам);
- каждый `ImageBlock` → один атом kind `image` (разворачивается в `<img>` data-URI, как
  в Этапе 1);
- каждый `CodeBlock` → один атом kind `code` (`<pre>`).

Один атомизатор обслуживает и текстовый источник, и pptx — оба дают `Section`.

#### 2. Контракт вывода ИИ (что модель обязана вернуть)

Системный промпт `EXACT_DESIGN_SYSTEM` — родственник `FREEFORM_SYSTEM` из `filler.py`
(те же бренд-правила, тот же allowlist классов, те же запреты), НО с иным заданием:

- Дано: пронумерованный список атомов (`id` + `text` + `kind`) одного слайда.
- Вернуть ТОЛЬКО ```html-блок с фрагментом контент-зоны, корень
  `<section class="slide" data-template="freeform">` (ассемблер сам переметит в `exact`).
- **Текст ставить ТОЛЬКО через метки** `{{aK}}` (грамматика метки: `{{` + id атома +
  необязательный диапазон слов `:i-j` + `}}`). Печатать сами слова из атомов — запрещено.
  Каждый атом использовать **ровно один раз** (в форме `{{aK}}` или `{{aK:i-j}}`).
- Первым элементом — шапка `<div class="content-head"><h3 class="content-head-title
  t-head-42">{{a1}}</h3></div>`, если есть атом-заголовок; иначе без шапки.
- Раскладка — обычным потоком (колонки `.row>.col`, карточки `.card`, число-герой
  `.t-number-320`, тезис `.t-hero-156`; максимум один `.accent-block`). Только классы из
  allowlist. Запрещено: `style=`, `<i>/<em>/<u>/<script>`, тени/градиенты/скругления.
- **Акценты (без печати слов):**
  - целый атом — обернуть его метку в акцент-поверхность (`.accent-block`, `.t-number-320`,
    `.t-hero-156`) или в `<b>` (разрешён; deck.css `b,strong{font-weight:600}`):
    `<div class="t-number-320">{{a4}}</div>`, `<b>{{a4}}</b>`;
  - **часть** фразы — метка с диапазоном слов `{{aK:i-j}}` (выделить слова с i-го по j-е,
    1-based, включительно): программа сама обернёт этот диапазон в `<b>` при рендере.
    Модель печатает только id атома и номера слов — сами слова не печатает, дословность
    цела. Один атом = одна метка (диапазон не отменяет вывод всего текста атома, он лишь
    помечает, какие слова жирные). `<i>/<em>/<u>` не использовать.

#### 3. Рендер меток → дословный html (детерминированно, в коде)

- каждую `{{aK}}` заменяем на HTML-escaped дословный текст атома (paragraph/list_item/
  heading); переводы строк paragraph → `<br>`;
- `table`/`image`/`code`-атомы разворачиваем той же логикой, что в `exact_builder.py`
  (переиспользовать `_block_html`);
- под-фразовые акценты: метку `{{aK:i-j}}` разворачиваем в **весь** дословный текст атома,
  оборачивая в `<b>` только слова с i-го по j-е (разбиение по пробельным группам, сами
  пробелы сохраняем — в `<b>` попадают ровно эти слова и разделители между ними, символ в
  символ); если диапазон выходит за число слов атома — акцент молча пропускаем, текст
  остаётся дословным целиком (текст важнее акцента);
- результат: `content={"html": <готовый фрагмент>, "exact": True}` — ассемблер завернёт в
  `.exact-zone/.exact-fit` без изменений.

#### 4. Проверки (гарантия дословности) + ретрай + фолбэк

После ответа ИИ (ДО подстановки текста, по «сырому» html с метками):

- **Чистота:** удаляем все метки `{{…}}` (в любой форме — `{{aK}}` или `{{aK:i-j}}`) и все
  теги; в остатке **не должно быть ни одной буквы/цифры** (иначе ИИ дописал прозу от себя)
  → провал.
- **Полнота:** множество id атомов, использованных в метках, == множество всех атомов,
  каждый ровно один раз (форма `{{aK}}` и `{{aK:i-j}}` считаются одним использованием `aK`;
  ничего не потеряно и не задублировано) → иначе провал.
- **Запрещённые приёмы:** переиспользовать `_FORBIDDEN_FRAGMENT` из `filler.py`.
- **Классы:** только `ALLOWED_CLASSES` (+ префиксы `m-`/`is-`) — переиспользовать
  `linter._is_allowed_class`.

Провал любой проверки → 1 повтор с конкретным замечанием (как ретраи в `_fill_freeform`).
Повтор тоже провалился → **фолбэк на детерминированный html этого слайда** (из
`build_exact_plan`). Текст никогда не искажается: в худшем случае слайд выглядит как в
Этапе 1.

#### 5. Оркестратор `design_exact_deck(client, doc, plan, *, workers=8, progress)`

- параллельно по слайдам (как `fill_deck`: `ThreadPoolExecutor`, гейт RPS у клиента);
- на каждый слайд: атомизировать соответствующую `Section` → вызвать ИИ → проверить →
  подставить → заменить `slide.content` designed-html; при провале оставить фолбэк-html;
- мягкая деградация: сбой одного слайда (`FillError`/транзиентный API) не валит деку —
  фолбэк, `warn` в progress (паттерн уже есть в `fill_deck`).

#### 6. Влезаемость (auto-fit)

Не меняем: designed-html идёт в `.exact-fit`, существующий JS движка ужимает шрифт под
`.exact-zone`. Перегруженный слайд → мелко, но 1-в-1 и дословно.

### Точка входа: правка `pipeline/build.py::_build_exact`

После `build_exact_plan(doc)`:

```
client = _exact_client_or_none(progress)   # KimiClient(); при RuntimeError (нет ключа) → None + warn
if client is not None:
    plan = design_exact_deck(client, doc, plan, progress=progress)
else:
    progress("warn: нет ключа к ИИ — точный перенос без дизайна (как Этап 1)")
return polish_plan(plan, out, theme=theme, vision=False, max_autofix=0, progress=progress)
```

`design_exact_deck` получает и `doc` (для атомов по секциям), и `plan` (слайды с
фолбэк-html и индексами). Сопоставление слайд↔секция — по порядку (оба 1-в-1).

## Границы слайдов в тексте (заменяет правило Этапа 1)

`parsers/exact_text.py` — гибкое авто-распознавание по приоритету (первый сработавший
уровень задаёт границы, остальные символы этого уровня — обычный текст):

1. есть метки `Слайд N:` (текущий регэксп) → режем по ним;
2. иначе есть строки-разделители `---` (горизонтальная черта на отдельной строке) →
   режем по ним;
3. иначе есть markdown-заголовки в начале строки (`#`/`##`, один верхний уровень) →
   каждый заголовок открывает слайд;
4. иначе — **весь текст = 1 слайд** + `progress`-подсказка «добавь разделители (`Слайд
   N:` / `---`), чтобы разбить на несколько слайдов».

Приоритет убирает риск «разрезать не там»: markdown-заголовки берутся только когда явных
разделителей нет. `ExactMarkerError` (жёсткая ошибка Этапа 1) больше не бросается —
пустого результата не будет. pptx этого не касается: там границы = слайды файла.

## Экономия токенов

Текущий exact = 0 токенов (детерминированный). Этап 2 добавляет 1 ИИ-вызов на слайд.
Экономию закладываем так, чтобы она помогала при поддержке кэша и ничего не ломала без неё.

1. **Кэш-дружелюбная раскладка промпта (главный рычаг).** Системное сообщение
   (`EXACT_DESIGN_SYSTEM` + бренд-правила + список классов + скелеты ≈ 1.5–2k токенов)
   — **неизменный префикс, байт в байт одинаковый на каждом слайде**; меняющиеся атомы
   — в самом конце (user-сообщение). OpenAI-совместимые провайдеры, кэширующие общий
   префикс, дадут скидку автоматически. `FREEFORM_SYSTEM` уже так устроен (строка
   постоянна, `ALLOWED_CLASSES` константа) — повторяем паттерн.
2. **Измерение вместо догадок.** Правка `pipeline/client.py`: сейчас `chat()` возвращает
   только `content` и **выбрасывает `resp.usage`**. Добавить сбор `usage`
   (`prompt_tokens`, `completion_tokens`, `prompt_tokens_details.cached_tokens`) и лог в
   `progress`/артефакты. Так увидим фактический расход и включился ли кэш (по
   `cached_tokens`). Закрыть тестом (мок transport с фейковым `usage`).
3. **Экономия без провайдера (работает всегда):** exact **не зовёт планировщик** (в auto
   он читает весь документ разом — минус один крупный вызов) и **не использует vision**;
   `thinking` выключен (`_FILL_NO_THINK`), ответы короткие; метки-заполнители на выходе
   короче полной прозы.
4. **Не строим свой кэш** — только раскладываем промпт правильно и меряем.

**Ориентировочная оценка (дека ~10 слайдов, оценки примерные, уточнятся по `usage`):**
без кэша ≈ 20–25k входных + ~3k выходных токенов на деку; общий системный префикс
(~15–18k из входных) при поддержке кэша даёт **−40…60% по входу**. Порядок цены —
как у обычной текстовой сборки той же длины **минус планировщик и минус vision**.

## Крайние случаи

- Нет ключа к ИИ / сбой сети → детерминированный дамп Этапа 1 (дека собирается).
- Провал проверки после ретрая на слайде → фолбэк-html этого слайда (остальные —
  задизайненные).
- Перегруженный слайд → JS-ужимание (не режем, не сокращаем).
- Таблица/картинка/диаграмма → атом, развёрнутый программой (ИИ не переписывает).
- Слайд только с заголовком / только с картинкой → рендерим (атом-заголовок / атом-image).
- Текст без разделителей → 1 слайд + подсказка (без ошибки).

## Тестирование (TDD)

- **Атомизация:** `Section` (все виды блоков) → атомы правильных kind/порядка;
  дословный текст символ-в-символ.
- **Рендер меток:** `{{aK}}` → дословный escaped-текст; таблица/картинка развёрнуты;
  диапазон `{{aK:i-j}}` → `<b>` ровно на словах i..j (текст атома дословный, целиком);
  диапазон за границей числа слов → без акцента, текст цел.
- **Проверка чистоты:** html с прозой мимо меток → провал; html только с метками → ок.
- **Проверка полноты:** пропущенный/задублированный атом → провал; все по разу → ок.
- **Фолбэк:** ИИ-мок, который «врёт» (пишет текст / теряет атом) → после ретрая на слайде
  оказывается детерминированный html; **дословность сохранена** (текст-подстрока в деке).
- **Нет ключа:** `_build_exact` без `CLOUDRU_API_KEY` → детерминированный результат, ИИ не
  зван (мок падает, если позвали).
- **Гибкие границы:** `Слайд N:` / `---` / `#`/`##` / без разделителей(=1 слайд) —
  правильное число слайдов, куски не путаются, дословность.
- **Экономия:** `client.chat` собирает `usage` из ответа (мок); при одинаковом системном
  префиксе он идентичен между вызовами (проверка кэш-дружелюбности).
- **Старый режим не задет:** `auto`/`rebrand` регресс-тесты зелёные; exact-слайды по-прежнему
  идут в `.exact-zone` (`data-template="exact"`).

## Вне рамок Этапа 2 / будущее

- Скриншот-референс оригинала (гибрид «текст + vision») — отклонён (цена/скорость/

- Конвертация EMF/WMF → PNG (наследие из Этапа 1) — не здесь.
- docx в exact — как текст с разделителями (у docx нет границ слайдов).

## Риски

- **Модель печатает текст мимо меток** чаще, чем хочется → страхует проверка чистоты +
  ретрай + детерминированный фолбэк (дословность не страдает никогда, страдает лишь
  «нарядность» отдельного слайда). Если провалов много — апгрейд до жёсткого структурного
  протокола (ИИ отдаёт JSON-раскладку регионов, а не html) — задел на будущее.
- **Cloud.ru не кэширует префикс** → экономия по п.1 не сработает; п.3 (без планировщика/
  vision) остаётся. Узнаем по `cached_tokens` на первом прогоне.
- **Нижний предел auto-fit** для очень плотных слайдов — наследие Этапа 1, здесь без
  изменений.
