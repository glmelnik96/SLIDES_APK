# Точный перенос (exact transfer) — дизайн

Дата: 2026-07-08
Статус: дизайн утверждён пользователем, ждёт review перед планом реализации

## Проблема

Текущая сборка деки (режим по умолчанию) намеренно **перекраивает** исходник:

1. **Планировщик перетасовывает контент.** `plan_deck` (для pptx — `_plan_deck_vision` по скриншотам, иначе `_plan_deck_text`) сам решает, сколько будет слайдов, под ориентир «6–18 слайдов», группирует разделы и следит за разнообразием шаблонов. Число и границы слайдов НЕ совпадают с исходником.
2. **Заполнитель переписывает текст.** `fill_deck`/`_fill_template` укладывает контент в слоты с лимитами (`max_chars`/`max_items`) и при переполнении **сокращает и переписывает** (в коде ретрай с командой «Сократи/исправь»). Даже `_fill_freeform` генерирует текст сам из брифа, а не переносит дословно.

Это отличный режим для «сырых» материалов, но он не подходит, когда у пользователя **уже есть готовый черновик** (чаще pptx, иногда текст с явной послайдовой структурой), где решено, что на каком слайде, и текст — константа.

## Цель

Добавить **отдельный пользовательский режим «Точный перенос»** со строгими гарантиями:

- **1 слайд источника → 1 слайд на выходе.** Никогда не разбиваем и не объединяем, даже если слайд перегружен.
- **Текст слово в слово.** Ничего не сокращаем, не дописываем, не перефразируем.
- **Картинки исходника переносим** на слайд как есть.
- Сверху — **оформление Cloud.ru** (фон, акцент, шрифты, колонтитул/логотип/номер).

Режим по умолчанию (авто-распределение) **остаётся без изменений** — новый режим добавляется рядом.

## Утверждённые решения (из брейншторма)

- **Путь В (смешанный).** Основа — надёжная детерминированная свободная раскладка (гарантирует «слово в слово», картинки, правило 1-в-1). Нарядные шаблоны — как «апгрейд» на Этапе 2. Пользователь выбрал «вариант 3».
- **Разметка границ в тексте — метки `Слайд N:`** (пользователь выбрал вариант 2). Например `Слайд 1:`, `Слайд 2:` в начале куска.
- **Нетекстовое содержимое — переносим картинки как есть** (пользователь выбрал вариант 2). В тексте картинок нет — актуально для pptx.
- **pptx читаем как данные, а не «зрением».** Дословность даёт только настоящий текст из файла (python-pptx), скриншот+LLM неизбежно перескажет.
- **В режиме exact ИИ-планировщик и ИИ-заполнитель не вызываются.** Раз текст трогать нельзя, а число слайдов задано — рендер полностью детерминированный.

## Пользовательский интерфейс

- На форме загрузки (`webapp`, шаблон формы + `create_job`) добавляем переключатель режима: **«Авто-распределение (как сейчас)»** (по умолчанию) и **«Точный перенос (1-в-1)»**.
- Выбор прокидываем тем же маршрутом, что уже проложен для булева `freeform_ok`: поле формы → `SessionInput` → раннер `worker/tasks/htmlnew.py` → `build_deck`. Точные сигнатуры сверяем при реализации по образцу `freeform_ok`.
- Типы файлов не меняем: `_ALLOWED["htmlnew"]` = `.md/.txt/.docx/.pptx`. В режиме exact тот же набор трактуется иначе (см. разбор).

## Архитектура и поток данных

Новое **значение build-режима `mode="exact"`** (рядом с текущими `auto`/`rebrand`). Сейчас build-режим выбирает `pick_mode(input_path)` внутри раннера (pptx→`rebrand`, иначе `auto`). В режиме «Точный перенос» выбор пользователя **перекрывает** `pick_mode`: раннер передаёт `mode="exact"` в `build_deck`.

Ветка `build_deck(mode="exact")` идёт в обход ИИ:

```
parse_file → exact_parse (per-slide units) → build_exact_plan (детерминированно, html на слайд)
           → polish/assemble
   (plan_deck и fill_deck НЕ вызываются)
```

### 1. Разбор источника → пер-слайдовые единицы

Единица источника: `{ title: str|None, blocks: [ {text, level} ... ], images: [bytes+тип] }`.

- **pptx (python-pptx):** идём по слайдам по порядку; с каждого:
  - заголовок — из title-плейсхолдера, если есть;
  - текст — из всех текстовых фреймов **дословно**, с сохранением абзацев, пунктов списка и их уровня вложенности (`paragraph.level`);
  - картинки — из picture-шейпов (`shape.image.blob` + `content_type`).
  - Один слайд pptx → одна единица. Порядок шейпов сохраняем.
- **текст/docx:** режем по меткам `Слайд N:` (регэксп в начале строки, регистронезависимо, допускаем `Слайд 1:` / `Слайд 1.` / пробелы). Первая непустая строка куска — заголовок, остальное — тело (абзацы = блоки; строки-списки сохраняем как пункты). Картинок нет.
  - Если меток нет ни одной — **понятная ошибка** с подсказкой, как разметить (не молчаливый фолбэк в 1 слайд, чтобы пользователь не получил случайный результат).

### 2. План 1-в-1 без ИИ

`build_exact_plan`: N единиц источника → N `SlidePlan`. Каждый слайд — `freeform=True`, а `content={"html": <детерминированный html>}` уже готов. Поскольку html присутствует, `fill_deck` для этих слайдов не нужен — ветка exact идёт мимо него сразу к сборке.

### 3. Детерминированный рендер слайда (свободная раскладка)

Новый **детерминированный билдер** формирует HTML-фрагмент контент-зоны того же вида, что и существующая freeform-раскладка (корень `<section class="slide" data-template="exact">` — отдельный маркер, чтобы отличать exact-слайды в QA/отладке; рендерится через тот же freeform-слот, `freeform=True`), только брендовые классы deck.css, но **без LLM**:

- шапка-заголовок (`.content-head` / `.t-head-42`) из `title`;
- тело — блоки дословно обычным потоком: абзацы `.t-body-30`, списки с сохранением уровней;
- зона под картинки (см. ниже).

HTML системный (доверенный), поэтому freeform-линтер (`FREEFORM_SYSTEM`/`_FORBIDDEN_FRAGMENT`, рассчитанный на вывод LLM) к нему **не применяем**. Для картинок нужен тег `<img>` — он вне текущего allowlist линтера, что ещё раз подтверждает: детерминированный exact-html линтуем отдельными правилами (структурная валидность), а не freeform-линтером.

### 4. Влезаемость (auto-fit) перегруженного слайда

Дека — фикс. 1920×1080; текст режима exact не сокращаем. Влезаемость решаем **подгонкой размера шрифта при загрузке в браузере** (движок деки уже инлайнит JS):

- на exact-слайдах контент-зона получает класс/`data`-метку;
- маленькая JS-процедура при загрузке уменьшает `font-size` тела, пока `scrollHeight <= clientHeight`, до **нижнего предела читаемости**;
- если упёрлись в предел, а контент всё ещё не влез — слайд всё равно рендерится (текст не теряем), но помечаем предупреждением в артефактах/прогрессе.

Чисто-CSS-решение не годится (не знает длину контента), поэтому auto-fit — в JS движка. Python может дополнительно ставить стартовый tier шрифта по грубой оценке длины, чтобы JS меньше итераций делал (необязательно на Этапе 1).

### 5. Картинки

- Извлечённые из pptx картинки встраиваем в HTML как **data-URI** (`<img src="data:{content_type};base64,...">`), чтобы дека осталась одним переносимым файлом (согласуется с текущим «self-contained» подходом деки).
- Раскладка: если у слайда есть картинки — делим зону на «текст + картинки»; если нет — текст на всю ширину.
- **Форматы:** растровые (PNG/JPEG) кладём напрямую. Векторные из Office (EMF/WMF) браузер не рендерит — на Этапе 1 такие **пропускаем с пометкой**; конвертацию в PNG выносим на Этап 2 (риск: требует внешней зависимости вроде LibreOffice/Pillow-плагина).

## Крайние случаи и обработка ошибок

- Слайд без текста (только картинка) — рендерим (одна картинка).
- Слайд только с заголовком — рендерим заголовок.
- Текст без единой метки `Слайд N:` — явная ошибка с инструкцией по разметке.
- Пустой источник / 0 слайдов — как сейчас: `LLMFormatError`-подобная понятная ошибка (пустую деку не собираем).
- Битая/неподдержанная картинка — пропуск с пометкой, слайд собирается без неё.
- Экстремально перегруженный слайд — auto-fit до предела + предупреждение, но текст цел.

## Тестирование

- **Разбор pptx:** N слайдов → N единиц; сверка текста **символ-в-символ** (дословность); подсчёт извлечённых картинок; сохранение уровней списка.
- **Разрез текста по `Слайд N:`:** правильные границы, куски не теряются и не путаются, дословность; отсутствие меток → ожидаемая ошибка.
- **План 1-в-1:** N единиц → N `SlidePlan`, все exact/freeform; **ИИ-клиент не вызывается** (мок падает, если позвали).
- **Сборка деки:** число слайдов == число единиц источника; текст присутствует дословно (подстрока в html); картинки встроены (data-URI); обе темы (dark/light) рендерятся.
- **Старый режим не задет:** дефолтный `auto`/`rebrand` проходит как прежде (регресс-тесты планировщика/заполнителя зелёные).

## Этапность

- **Этап 1 (MVP, выполняет все жёсткие правила):** переключатель UI + проброс режима; разбор pptx и текста (дословно); детерминированная свободная раскладка 1-в-1; JS auto-fit; встраивание растровых картинок (PNG/JPEG); векторные — пропуск с пометкой; тесты.
- **Этап 2 (докрутка):** «апгрейд» простых слайдов в нарядные бренд-шаблоны (полный «вариант 3»); конвертация EMF/WMF в PNG.

## Открытые вопросы / риски

- **Точки подключения режима** (имя поля формы, поле `SessionInput`, место перекрытия `pick_mode`) — сверить по образцу `freeform_ok` при реализации.
- **EMF/WMF** — надёжной конвертации без внешней зависимости нет; Этап 1 их пропускает.
- **Нижний предел шрифта** для auto-fit — подобрать значение, при котором очень плотный слайд остаётся читаемым; согласовать порог предупреждения.
- **docx в exact-режиме** трактуем как текст с метками `Слайд N:` (у docx нет собственных границ слайдов); подтвердить, что это ожидаемо.
