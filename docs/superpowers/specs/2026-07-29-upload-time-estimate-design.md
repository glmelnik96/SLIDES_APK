# Оценка времени сборки при загрузке документа

Дата: 2026-07-29 · Статус: утверждён Глебом (вариант «неблокирующая оценка у каждой сборки», механика А)

## Проблема

Потолок деки поднят до 100 слайдов (`MAX_DECK_SLIDES`, htmlslides/pipeline/build.py),
крупный документ — легальный вход. Но сборка 40+ слайдов идёт 15–20+ минут, и
пользователь узнаёт об этом только по факту, глядя на прогресс. Нужно показать
ожидаемое время сразу при постановке в очередь.

## Решение (утверждённые ответы)

- **Неблокирующее**: сборка стартует сразу, оценка — строка в карточке
  прогресса/очереди. Никаких диалогов подтверждения.
- **У каждой сборки**: нейтральная строка всегда; для крупных (>20 разделов) —
  предупреждающий тон. «Предупреждение» — градация тона, не отдельный механизм.
- **Механика А**: сервер считает разделы в `/api/jobs` реальным парсером
  (`htmlslides.parsers.base.parse_file`) — та же правда, что у сборки.
  Двойной парсинг (второй раз в воркере) — миллисекунды на фоне LLM-этапов.

## Сервер

1. В `/api/jobs` после записи файла в сессию:
   `try: section_count = len(parse_file(dest).sections); except Exception: section_count = None`.
   Падение парсера НЕ блокирует запуск — реальную ошибку покажет воркер.
2. Новая nullable-колонка `jobs.section_count` + мини-миграция на старте
   (SQLite `ALTER TABLE jobs ADD COLUMN`, по существующему паттерну схемы).
3. `section_count` отдаётся в ответе `POST /api/jobs`, в `/api/jobs/active`
   и в `/api/jobs/{id}/status` — оценка переживает перезагрузку страницы и
   видна ещё в очереди.

## Клиент

- Минуты считает клиент: `max(2, Math.round(n * 0.5))` — калибровка по замерам
  (~25–30 с на слайд: 10 разделов → 5 мин, 40 → 20 мин). Формула — в одном
  месте app.js, чистой функцией.
- Строка в карточке прогресса и очереди: «N разделов · примерно X мин»
  (для .pptx — «N слайдов»). ≤20 разделов — нейтральный muted-текст; >20 —
  предупреждающий тон + приписка «крупный документ — сборка займёт заметное время».
- >100 разделов — добавка «соберём первые 100» (реальное поведение `_cap_sections`).
- `section_count == null` — строки нет, поведение как раньше.

## Тесты

- API (tests/test_app.py): ответ `/api/jobs` несёт `section_count` для md с
  известным числом секций; битый файл → сборка стартует, `section_count: null`;
  `/api/jobs/active` и `/status` несут поле; миграция на существующей базе
  не падает.
- JS (tests/js): чистая функция «count → {минуты, текст, тон}» — формула минут,
  разделы/слайды по расширению, порог 20, кап 100.

## Сознательно НЕ делаем

- Отдельный precheck-эндпоинт до нажатия «Создать» (файл гонялся бы дважды).
- Оценку в истории завершённых сборок (там она не нужна).
- Отдельную формулу для exact-режима (оценка и так «примерно»).
- Блокирующий диалог подтверждения (отвергнут при обсуждении).
