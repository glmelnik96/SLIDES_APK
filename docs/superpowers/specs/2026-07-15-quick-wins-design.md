# Quick Wins (Slice A) — дизайн-документ

**Дата:** 2026-07-15
**Источник:** `slides_apk_audit.md`, раздел 7 «Quick wins»
**Цель:** самые дешёвые правки конструктора/чат-режима/первого экрана,
повышающие интуитивность, — все укладываются в текущую архитектуру, без изменения
пайплайна генерации и без новых зависимостей.

> **Изменение объёма (2026-07-15):** пункт «словарь русских лейблов полей/макетов»
> **исключён** по решению заказчика. Осталось четыре правки. Русские тексты, которые
> раньше жили бы в общем словаре, теперь держим маленькими константами рядом с кодом,
> который их использует.

## Не-цели (чего НЕ делаем в этом слайсе)

- Не трогаем LLM-пайплайн, планировщик, «Точный перенос».
- Не меняем слот-контракт (`library.json`, `library.py`) и формат `plan.json`.
- Не добавляем WYSIWYG/канвас — модель редактирования остаётся панельной.
- Не меняем серверные эндпоинты.
- Не вводим словарь технических id → русских лейблов (исключено из объёма).

## Технологии

FastAPI + ванильный JS. Правки почти целиком во фронте: `webapp/static/editor.js`,
`webapp/static/index.html`, `webapp/static/styles.css`. Для подсветки (п.4)
добавляются `data-slot` в Jinja-мастера (`htmlslides/templates/slides/*.html`) и одно
правило в `htmlslides/engine/deck.css`.

## Общий принцип

Каждый пункт — изолированное изменение слоя отображения. Данные (автосейв, ошибки
валидации, лимиты, поля типизированных слайдов) **уже существуют** — мы их только
показываем человеку понятнее. Ничего не «пропадает»: незнакомый код ошибки/слот
деградирует мягко (показываем как есть или молчим, форму не ломаем).

### Единый визуальный стиль (обязательное требование ко всем пунктам)

Новые детали не должны выглядеть инородно — переиспользуем то, что уже есть в
`styles.css`, а не изобретаем свой вид.

- **Токены цвета:** `--accent` (#26D07C, зелёный — успех/акцент), `--danger`
  (#ff6b6b, ошибки), `--muted` (второстепенный текст), палитра `--warn-*` (жёлтые
  предупреждения). Не вводим новых цветов.
- **Скругления = 0.** В теме `--r/--r-sm/--r-lg` равны `0px` (острые углы повсюду).
  Любой новый блок — без `border-radius` (или `var(--r)`).
- **Шрифты:** `--font-display` (SB Sans Display), `--font-text` (SB Sans Text). Своих
  не подключаем.
- **Готовые компоненты для переиспользования:** подсказки — класс `.field-hint`
  (узел из `hint()` в editor.js); ошибка поля — уже есть `.field-error` (красит рамку
  в `--danger`); кнопки — `.btn`, `.btn-sm`, `.btn-ghost`, `.btn-danger`, `.btn-link`;
  строка списка конструктора — `.field-item`; шапка формы — `.builder-head`; карточки
  входа — `.entry-card`/`.is-active` (акцент через inset-тень). Новые элементы
  наследуют отступы/типографику этих классов.

## 1. Статус «Сохранено ✓» + текст ошибки под полем + счётчик символов

**Проблема.** Автосейв идёт молча; ошибки валидации показаны только красной рамкой
без слов; лимит символов молча режет текст (эвр. 1 «видимость статуса»,
9 «понятные ошибки»; Baymard).

**Решение.** Данные уже есть — показываем словами, в существующем стиле.
- **«Сохранено ✓».** В `saveCurrentSlide` (стр. 649–659) после успешного PUT показываем
  ненавязчивый статус в шапке формы (`.builder-head`), при неудаче — «Не сохранено»
  вместо резкого `alert()` на каждый сбой (alert оставляем только как крайний фолбэк).
  Три состояния: «Сохранение…» (`--muted`), «Сохранено ✓» (`--accent`),
  «Ошибка сохранения» (`--danger`). Статус приглушённо гаснет через пару секунд.
- **Текст ошибки под полем.** `markFieldErrors` (стр. 662) сейчас только красит рамку
  (`.field-error`). Дополняем: под проблемным полем печатаем сообщение — узел в стиле
  `.field-hint`, но цветом `--danger` (напр. модификатор `.field-hint--error`). Карта
  кодов (чистая функция `errText(code, detail)`):
  - `missing_required` → «Заполните обязательное поле».
  - `too_long` (detail «N > max») → «Слишком длинно: N из max символов».
  - `too_many_items` (detail «N > max») → «Слишком много пунктов: N из max».
  - `unknown_slot` → не показываем пользователю (внутреннее).
  Текст печатается **под конкретным полем** — оно уже визуально привязано, поэтому имя
  поля внутри сообщения не требуется (словаря лейблов нет).
- **Счётчик символов.** В `renderSlot` (стр. 524/530) вместо статичного `hint(до N
  символов)` — живой счётчик «M/N» тем же узлом `.field-hint`, обновляется на `input`,
  переключается на `--danger` при M > N.

**Ключевое решение.** Русские строки (три состояния статуса + `errText`) держим
маленькой константой/функцией рядом с кодом в `editor.js` — отдельного словаря нет.
Пункт самодостаточен, ни от чего не зависит, поэтому идёт первым.

**Критерии приёмки.**
- После правки поля появляется «Сохранено ✓» (и «Сохранение…» на время запроса), цвета
  из токенов.
- При превышении лимита/пустом обязательном поле под полем виден понятный русский текст
  в стиле подсказок (не «выпадает» из вёрстки).
- Счётчик «M/N» отражает текущую длину и краснеет (`--danger`) при переполнении.
- Сетевой сбой сохранения показан словами, без каскада `alert()`.
- Юнит-тест на `errText(code, detail)`: разбирает «N > max», возвращает верную строку
  для каждого кода.

## 2. Главная кнопка «Загрузить документ» на первом экране

**Проблема.** «Непонятно, с чего начать»: три равнозначные карточки + два плотных
абзаца интро = перегруз выбором (закон Хика; NN/g про empty states).

**Решение.**
- **Иерархия карточек.** Карточка 01 «Загрузить документ» — главная (крупнее, акцентная),
  02 «Заполнить шаблон» и 03 «Собрать в чате» — тише (вторичный стиль). Реализация в
  `styles.css` (`.entry-cards`, стр. 115+): вместо `repeat(3,1fr)` — раскладка «одна
  главная сверху на всю ширину + две тихие в ряд под ней», плюс модификатор
  `.entry-card--primary`. Акцент делаем тем же приёмом, что уже есть у `.is-active`
  (inset-тень `--accent`), без новых цветов и без скруглений.
- **Сжатие интро.** Два абзаца `.intro-lead` (`index.html` стр. 28–29) → одна короткая
  строка-суть + раскрывашка «Подробнее» (`<details>`), в которой прячется нынешний
  подробный текст (форматы, совет про markdown). Прогрессивное раскрытие.

**Обязательно сохранить.** Логику `app.js`: обработчик клика по `.entry-card`
(стр. 385–397), `startDraft` (стр. 364), карту `ENTRY_CTA` (стр. 382), восстановление
на `pageshow` (стр. 401). Класс `is-active` для upload и показ `#uploadFlow` работают
как раньше. Галочку «Точный перенос» (`#exactTransfer`, `index.html` стр. 75–82) не
трогаем — она остаётся внутри блока загрузки.

**Разрешённое расхождение с аудитом.** Аудит писал, что на `main` входы 02/03 скрыты;
в текущей ветке видны все три (проверено — CSS-грид на 3 колонки, JS не прячет). Поэтому
задача — только визуальная иерархия и сжатие интро, без «показать скрытое».

**Ключевое решение.** Меняем только вёрстку/стили и один `<details>`; JS точек входа
не переписываем, чтобы не сломать три сценария и exact-галочку.

**Критерии приёмки.**
- На первом экране визуально доминирует «Загрузить документ»; 02/03 явно вторичны,
  но в общем стиле (острые углы, акцент из токенов).
- Интро — одна строка + «Подробнее» с прежним текстом внутри.
- Все три входа работают как раньше; галочка «Точный перенос» на месте; возврат Back
  восстанавливает карточки (pageshow) без «залипшего Создаю…».
- Проверка обеих тем (dark/light) и узкой ширины.

## 3. Построчные инпуты вместо «|»-синтаксиса в чат-режиме

**Проблема.** В карточках полей чат-режима (`renderFieldCard`, стр. 881) списки
редактируются одним полем через разделитель « | »: пункты (`bullets`), пары
цифра=подпись (`stats`), две колонки (`two_col.left/right`). Самый хрупкий ввод: легко
сломать структуру одной опечаткой в разделителе (эвр. 5 «предотвращение ошибок»).

**Решение.** Строим маленький построчный редактор-репитер для трёх форм полей и
подключаем его в `renderFieldCard` вместо `fieldInput(... .join(" | "))`. Визуально
повторяем строку `.field-item` конструктора и кнопки `.btn-sm`/`.btn-ghost`/`.btn-danger`,
чтобы вид совпадал с уже существующим редактором списков:
- `bullets`: строки → по строке на инпут, кнопка «+ пункт», удаление ✕.
- `stats`: пары → две ячейки в ряд («значение», «подпись»), «+ пункт», ✕.
- `two_col`: две колонки, в каждой — построчный список.
Данные пишем прямо в `f.bullets` / `f.stats` / `f.left` / `f.right` (те же формы,
что и раньше) и вызываем существующий `saveFields` (стр. 848) — контракт эндпоинта
`/fields` не меняется.

**Ключевое решение (точность против аудита).** Аудит предлагал «переиспользовать
`renderItem`». Но `renderItem` (стр. 559) завязан на `spec.item_slots`/`collectContent`
конструктора, а у типизированных полей модель проще (массивы строк и `{value,label}`).
Поэтому делаем **аналогичный** компактный репитер под эти формы, а не буквальный
reuse. Логика «строка ↔ элемент массива» одна и та же — визуально и по UX совпадает
с конструктором.

**Критерии приёмки.**
- В чат-режиме `bullets`/`stats`/`two_col` редактируются построчно, без « | ».
- Кнопки/строки визуально те же, что в конструкторе (`.field-item`, `.btn-*`).
- Добавление/удаление строки сразу отражается в превью (через `saveFields`→`loadDeck`).
- Payload на `/fields` сохраняет прежнюю форму (`{slide_type, fields}` с массивами).
- Подсказки про « | » убраны (`appendHint`, стр. 912/923/934).

## 4. Подсветка редактируемого элемента на слайде

**Проблема.** Панельное редактирование «слепое»: правишь поле слева — не видно,
какому месту на слайде оно соответствует (эвр. 1 «видимость статуса», 6 «узнавание»).

**Решение (упрощённое против аудита).** `#deck` — iframe **того же origin**
(`frame.contentDocument` уже используется в editor.js), поэтому не нужен postMessage:
подсветку делаем прямым доступом к DOM слайда.
- **Движок:** в Jinja-мастера добавляем `data-slot="<имя слота>"` на элемент,
  который рендерит слот верхнего уровня (текст → его тег; список/группа → контейнер).
  Плюс одно правило в `htmlslides/engine/deck.css`:
  `.slot-highlight { outline: 2px solid var(--accent); outline-offset: 3px; }`
  — **без** `border-radius` (в теме острые углы), цвет из токена.
- **Редактор:** в `renderSlot` у полей уже проставлен `dataset.slot`
  (стр. 463, 526, 534, 562), а `markFieldErrors` уже читает `[data-slot]` (стр. 665) —
  инфраструктура на месте. Добавляем `focusin`/`focusout` на форме: по фокусу читаем
  `slot`, находим в `frame.contentDocument` элемент `[data-slot=slot]` и вешаем/снимаем
  класс `.slot-highlight` (при необходимости `scrollIntoView`).

**Границы (scope).** Подсветка работает для слотов **верхнего уровня** конструктора
(текст/список/группа → соответствующий элемент-обёртка). Внутренности графиков (бары
SVG) и отдельные пункты списка отдельными маркерами не размечаем — маркер вешаем на
контейнер. На exact/freeform-слайдах `data-slot` нет — подсветка просто не срабатывает
(ожидаемо, ошибок не даёт).

**Почему это самый тяжёлый пункт.** Трогает ~23 мастера — общие с обычным и «Точным
переносом». Разметку нельзя ломать: добавляем только атрибут-хук, без изменения
геометрии. Делаем последним, отдельным мини-проектом.

**Ключевое решение (+ альтернатива).** Прямой доступ к DOM (same-origin) вместо
postMessage — меньше кода, не трогаем `deck.js`. Альтернатива (postMessage + слушатель
в деке) оставлена в резерве на случай, если превью когда-то станет cross-origin.

**Критерии приёмки.**
- Фокус на поле в конструкторе → соответствующий блок на слайде получает обводку
  (`--accent`, острые углы); снятие фокуса → обводка исчезает.
- Ни один мастер не «поехал» визуально от добавления `data-slot` (сверка шотами
  до/после по каждому типу).
- Обычный режим и «Точный перенос» рендерятся без ошибок.

## Порядок и зависимости

1. **П.1 статус/ошибки/счётчик** — самодостаточен (свои русские строки рядом с кодом).
2. **П.2 первый экран** — независим; в основном вёрстка/стили.
3. **П.3 построчные инпуты** — независим.
4. **П.4 подсветка** — тяжёлый, последним; отдельная сверка шотами по мастерам.

Пункты слабо связаны; порядок — от самого дешёвого/полезного к самому трудоёмкому.

## Тестирование

- **Юнит (pytest/JS):** чистая функция `errText(code, detail)` из п.1 — разбор «N > max»
  и текст для каждого кода.
- **Визуально:** существующий playwright-харнесс (`_shots/`) — шоты конструктора,
  чат-режима и первого экрана до/после, обе темы; для п.4 — шот каждого типа мастера
  до/после добавления `data-slot` (проверка «ничего не поехало»).
- **Ручной сценарий:** пройти три входа, автосейв, превышение лимита, построчный ввод.
