# Недоступность модели: быстрый отказ, автофолбэк на резерв, честная ошибка

**Дата:** 2026-08-04
**Инцидент:** 2026-08-04, 13:21 и 13:23 MSK — `MiniMaxAI/MiniMax-M3` перестала
отвечать на стороне Cloud.ru (`APITimeoutError: Request timed out` на КАЖДОМ вызове;
проба с прода в 13:50: MiniMax — таймаут 45 с, `moonshotai/Kimi-K2.6` — 1,9 с, ОК).
Обе сборки получили `planner.section_fallback` на всех разделах, ползли 17–18 минут
и закончились `cancelled` — пользователь не дождался.

## Что сломано

1. **Нет фолбэка.** `KimiClient.model` выбирается один раз в `__init__` и не меняется
   никогда. Откат только руками: env `CLOUDRU_MODEL` + рестарт сервиса.
2. **Нет быстрого отказа.** Один вызов при мёртвой модели стоит
   `DEFAULT_TIMEOUT × (DEFAULT_MAX_RETRIES + 1)` = 180 × 3 = 9 минут. Пайплайн
   узнаёт о недоступности только через эти 9 минут, и так на каждой фазе.
3. **Тихая деградация.** `TRANSIENT_API_ERRORS` (таймаут/обрыв/лимит/5xx) гасятся
   пофазно: раздел → эвристический слайд (`planner.py`), слайд → `blank`
   (`filler.py`), vision-QA/autofix пропускаются (`build.py`). При ПОЛНОЙ
   недоступности провайдера сборка заканчивается `done` декой из заглушек: все
   предупреждения идут префиксом `warn:`, который UI намеренно скрывает
   (`app.js`), а сетка «пустой результат» в `runner.py` пропускает — файл-то есть.
   Гард `build.py` ловит только `slides == []`, а не «все слайды деградировали».
4. **Текст ошибки не различает «модели нет».** 404 → «Сервис ИИ вернул ошибку
   (код 404). Повторите запуск» — совет заведомо бесполезный: модель снята.

## Решение

### 1. Резервная модель, липкое переключение (client.py)

`FALLBACK_MODEL = "moonshotai/Kimi-K2.6"` (мультимодальная, была дефолтом до
`339298a` — то есть заведомо тянет весь пайплайн, включая vision). Переопределяется
env `CLOUDRU_FALLBACK_MODEL`; пустая строка = резерва нет.

Переключение **липкое и одноразовое**: назад не возвращаемся. Иначе на
деградирующем шлюзе клиент бы метался между моделями, платя по 9 минут за пробу.

Триггеров два:

- **Preflight-проба** (`KimiClient.preflight`) — крошечный вызов с коротким
  таймаутом (`PROBE_TIMEOUT = 30 с`, `max_retries=0`, `max_tokens=256`: ниже 256
  MiniMax отдаёт пустой content, см. `project_model_minimax`). Зовётся один раз в
  начале сборки. Здоровый провайдер стоит ~2 с и несколько токенов.
- **Порог по ходу сборки** — `SWITCH_AFTER = 3` транзиентных сбоя подряд. Ловит
  деградацию, начавшуюся ПОСЛЕ пробы. Счёт ведём в `chat_ex` — единственной точке,
  через которую проходят все вызовы пайплайна.

Зовёт пробу `build_deck` — ПЕРВЫМ действием, до парса и рендера исходника (после
них экономить уже нечего). Тем же вызовом клиент узнаёт, куда слать `notice:`.

Если резерв тоже не отвечает на пробе → `ProviderUnavailable` сразу, до планирования.
Пользователь получает внятный отказ за полминуты вместо 40 минут ожидания.

### 2. Гард «дека из заглушек» (planner.py, filler.py)

`_plan_section` возвращает `(slides, api_degraded)` и `fill_deck` считает свои
деградации — обе фазы отличают сбой API от осечки формата. Если так деградировало
**больше половины** разделов/слайдов → `ProviderUnavailable`. Правило одно на обе
фазы — `client.degradation_is_total(degraded, total)` (строго больше половины),
иначе «дека из заглушек» пролезла бы через ту фазу, что забыла про порог. Это сетка
на случай, когда лежат ОБЕ модели: лучше честный отказ, чем «успех» с пустой декой.

Порог, а не «хоть один»: единичный блип штатно стоит одного слайда, и так было
задумано (комментарии в `filler.py`/`build.py` про прод-сбой 2026-07-28).

### 3. Видимость и текст (build_errors.py, app.js)

- Новый префикс прогресса `notice:` — решения, принятые за пользователя, показываем
  дословно (как `limit:`). Отдельный от `limit:` намеренно: `runner.py` считает
  `limit:` признаком обрезки деки и пишет `truncated` в статистику; переезд на
  резервную модель — не обрезка, и метрику пачкать нельзя.
- `ProviderUnavailable` → код `provider_unavailable`, текст без ложного «повторите
  запуск».
- `openai.NotFoundError` (модель снята/имя неверное) → тот же код, свой текст:
  повтор не поможет, нужен администратор.

## Не делаем

- Не переключаем прод на Kimi насовсем (решение Глеба 2026-08-04): MiniMax
  выигрывает A/B (`project_model_minimax`), резерв — только на время недоступности.
- Не ретраим ту же фазу на резерве задним числом: уже деградировавшие разделы
  остаются деградированными. Перепланировать полдеки — это ещё десятки минут,
  а гард из п.2 не даст отдать мусор молча.
