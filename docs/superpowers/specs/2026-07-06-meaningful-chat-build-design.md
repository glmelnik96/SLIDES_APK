# Осмысленная сборка деки в диалоге с ассистентом

Дата: 2026-07-06
Статус: дизайн утверждён, ждёт review перед планом реализации

## Проблема

Текущая сборка деки в чате технически работает, но переживается как «кот в мешке»:

1. **Невидимый enrich.** Аутлайн показывает `content.title || brief`. Когда у слайда есть заголовок, обогащённый `brief` не виден — правки контента не отражаются в UI.
2. **Монолитная молчаливая сборка.** `build_outline` синхронно гоняет `_pick_template` + `fill_slide` (~2 LLM-вызова) на каждый слайд, без стриминга прогресса. Пользователь видит только оверлей «Собираю деку…».
3. **Вводящий в заблуждение оверлей.** Приписка «можно закрыть страницу, сборка идёт на сервере» относится к длинному асинхронному билду, а чат-сборка синхронная и быстрая.

Итог: диалог с ассистентом идёт «вслепую» — модель что-то решает под капотом (какой шаблон, как разложить контент), а пользователь узнаёт результат только после рендера.

## Цель

Перевести сборку в модель **«сначала утверждаем контент текстом, потом детерминированный рендер»**: весь смысловой диалог идёт ДО рендера, на уровне видимых и редактируемых полей слайда. Сам рендер для типовых слайдов — быстрый и предсказуемый: что видел в аутлайне, то и на слайде.

## Утверждённые решения

- **Модель C (content-first):** диалог по тексту/полям до рендера; «сборка» рендерит утверждённое.
- **Единица правки B (структурированные поля):** на каждом слайде — реальные поля будущего слайда, не свободный абзац.
- **Типизация + fallback:** 4-5 типов слайдов покрывают ~80% детерминированно; редкое/сложное падает на старый LLM-fill.
- **Гибрид правки:** чат-ассистент предлагает структурированные поля из брифа → пользователь дочищает их inline в аутлайне.
- **Архитектура (Подход 1):** типизированный контент живёт прямо в `Slide` (единый источник правды, `DeckPlan-as-truth`); отсутствие типа = сырой слайд на старом рендере (естественный fallback).

## Модель данных

`Slide` расширяется опциональными полями:

```
Slide:
  ...существующие (title, brief, filled, freeform, template_id, content-html)...
  slide_type: Literal["title","bullets","stats","two_col","quote"] | None   # None = сырой
  fields: dict | None   # структурированные поля под slide_type
```

Схема `fields` по типам (строгая, валидируется отдельной Pydantic-моделью на каждый тип):

| `slide_type` | `fields` |
|---|---|
| `title` | `heading`, `subtitle?` |
| `bullets` | `heading`, `bullets: list[str]` (2-6) |
| `stats` | `heading`, `stats: list[{value, label}]` (2-4) |
| `two_col` | `heading`, `left: list[str]`, `right: list[str]` |
| `quote` | `quote`, `author?` |

Состояния слайда:

- **сырой** — `slide_type is None`, есть только `brief`; рендер через `_pick_template` + `fill_slide` (fallback).
- **типизированный** — `slide_type` задан, `fields` валидны; детерминированный рендер по типу, без LLM.
- `filled` — флаг «уже отрендерен в `content`-html» (кэш).

Старые черновики без `slide_type` работают как раньше — миграция не нужна.

## Чат-агент

Один новый intent — `propose_content`. Остальные intents без изменений.

- **`classify()`** получает action `propose_content` для запросов «предложи контент / разложи по полям / структурируй». Формулировки «дополни детали» остаются на `enrich` (работает по тексту brief).
- **`_propose_content(client, plan, message)`:**
  1. Цель — сырые слайды: `[i for i,s in enumerate(plan.slides,1) if s.brief and s.slide_type is None and not s.freeform]` (можно сузить до конкретного номера, если указан).
  2. Один LLM-вызов → на каждый слайд `{index, slide_type, fields}`. Системный промпт — жёсткий JSON-контракт (по образцу надёжного `_OUTLINE_SYSTEM`) с описанием 5 типов и их полей; модель сама выбирает тип под смысл.
  3. Валидация: каждый элемент валидируется Pydantic-моделью соответствующего типа. Нераспознанный тип / невалидные `fields` → слайд остаётся сырым (не роняем весь ответ).
  4. `max_tokens ≥ 4000` (урок enrich-бага: типизация всей деки — большой JSON; диагностировать на реалистичном размере контекста, не на синтетике).
  5. Ответ в чат: «Разложил по полям N слайдов. Проверь и поправь в аутлайне — потом жми "Собрать".»
- **`build_now`** остаётся nudge'ом (сборку инициирует пользователь). **`enrich`** без изменений.

Модели: дискриминированный union `ProposedSlide` по `slide_type`; ответ `ProposedContent(slides: list[ProposedSlide])`.

## Рендер

`render_draft()` — развилка по состоянию слайда:

```
для каждого slide:
  если slide.filled и есть content-html → готовый html (кэш)
  иначе если slide_type задан → render_typed(slide_type, fields)   # детерминированно, без LLM
  иначе → _pick_template + fill_slide                              # fallback, LLM
```

- **`render_typed(slide_type, fields)`** — чистая функция без LLM. Пять маленьких рендер-функций (по типу), каждая возвращает `content`-html того же формата, что пишет `fill_slide` → ниже по пайплайну ничего не меняется.
- **Маппинг тип → шаблон движка** подбирается из существующих шаблонов (обложка, список, статы, две колонки, цитата) и фиксируется в коде (не в промпте). Если точного шаблона нет — ближайший, маппинг захардкожен.
- Типизированный рендер идемпотентен и мгновенен: «сборка» перестаёт быть чёрным ящиком. LLM работает только на сырых/fallback-слайдах.
- **Инвалидация кэша:** правка `fields` в аутлайне → `filled=False` для слайда → следующий рендер пересобирает только его.

## Аутлайн и правка (UI)

`renderOutline` рендерит строку по состоянию слайда:

- **сырой слайд** — как сейчас (заголовок + серый brief) + чип «сырой» + действие «Предложить контент» (шлёт в чат intent `propose_content`).
- **типизированный слайд** — раскрытая карточка с inline-редактируемыми полями по типу (`heading`, буллеты/статы/колонки/цитата) + чип с типом. Чинит «невидимый enrich»: видно ровно то, что уйдёт в рендер.

Правка полей: debounced `PATCH /api/drafts/{id}/slides/{i}` с новыми `fields` → сервер валидирует по типу, пишет в plan, ставит `filled=False`. Переиспользуется debounce-паттерн ручного конструктора (тот, где чинили потерю последней правки).

Смена типа: селектор типа на карточке (если модель выбрала не тот); смена переинициализирует поля под новую схему.

## Сборка (trigger)

Кнопка «Собрать» (бывшая «Заполнить слайды») дёргает существующий синхронный `POST /api/drafts/{id}/build`.

- Для типизированных слайдов рендер мгновенный и предсказуемый; LLM крутится только на сырых.
- Оверлей: убрать приписку про «можно закрыть страницу, сборка на сервере» (она про асинхронный длинный build). Показывать честный прогресс «Рендерю слайд N из M». Для чисто типизированной деки оверлей мелькнёт и исчезнет.

## Обработка ошибок

- Невалидный `fields` от LLM или от PATCH → слайд остаётся/помечается сырым, не роняем ответ; пользователю видно, что слайд «сырой» и требует внимания.
- Пустой/усечённый ответ `_propose_content` → сохраняем сырое состояние, сообщаем в чат, что не удалось разложить (без падения).
- Существующий guard `build` («нечего собирать — аутлайн пуст») сохраняется.

## Тестирование

- Юнит: валидация `fields` по каждому типу (валидные/невалидные кейсы).
- `render_typed` per-type → корректный `content`-html; идемпотентность.
- `render_draft` развилка: типизированный → без LLM; сырой → fallback-путь вызывается.
- `_propose_content`: сырые слайды типизируются; невалидный элемент оставляет слайд сырым; enrich/другие intents не задеты.
- `classify` разводит `propose_content` vs `enrich`.
- PATCH slides: валидный `fields` пишется + `filled=False`; невалидный отклоняется.
- Регресс: старые черновики без `slide_type` рендерятся старым путём (миграция не нужна).
- Диагностика LLM-вызовов — на реалистичном размере контекста (урок enrich-бага о `max_tokens`).

## Вне scope

- Асинхронная/стримящая сборка с прогрессом по слайдам в чате (модель A) — сознательно не берём.
- Расширение набора типов сверх 5 — по мере надобности, отдельно.
- Изменение самих шаблонов движка.
