# Перезапуск сборки + плашка доступности ИИ

**Дата:** 2026-08-05 · **Приложение:** App2 `/slides`

Две независимые правки главной страницы, обе про один и тот же разрыв: пользователь
не понимает, что делать, когда сборка не удалась, и не знает, стоит ли вообще
запускать новую.

---

## 1. «Повторить» — серверный перезапуск

### Что было

Кнопка «Повторить» на карточке сбоя (`app.js`, `cardActions`) звала `retryUpload()`:
скролл к дропзоне + `createJob()`, если файл ещё выбран в `<input type=file>`.
После F5 (а перезагрузка — обычное дело, когда сборка упала) выбор файла пропадает,
и кнопка превращается в «прокрутить страницу вверх». Ни один пользователь не
догадается, что она сделала.

### Решение

`POST /api/jobs/{session_id}/retry` — перезапуск на стороне сервера из **сохранённого
исходника** сессии.

- Владение и статус проверяются как в `/cancel` (`_owned_or_404` → 404 чужому).
- Разрешены только `failed` и `cancelled`; `kind="draft"` не перезапускается этим
  эндпоинтом (у черновика своя кнопка «Продолжить»).
- Исходник ищем как `session_dir(sid)/input.*`, копируем в каталог **новой** сессии
  и ставим новую джобу с тем же `mode`, `source_filename` и `exact_transfer`.
- Лимиты (`MAX_ACTIVE`, per-user) — через общий хвост постановки в очередь
  `_start_build`, а не своей копией: перезапуск не должен быть дырой в лимитах.
- Ответ — той же формы, что у `POST /api/jobs`, чтобы клиент просто позвал
  `streamProgress`.

### Развилка: где брать исходник

- ❌ **Клиент помнит файл** — не переживает F5, то есть не решает исходную проблему.
- ❌ **Хранить исходники дольше 24 ч ради retry** — ломает обещанный ретеншен
  клиентских данных ради удобства кнопки. Неприемлемый размен.
- ✅ **Работает, пока жив исходник в `session_dir`** — то есть ровно в окне
  ретеншена, а когда файла нет, говорим об этом честно: **410** с текстом
  «Исходник больше не хранится — мы удаляем файлы через 24 часа. Загрузите файл
  заново». Тупик с объяснением лучше кнопки, которая молча ничего не делает.

### Схема

`jobs.exact_transfer` (INTEGER, nullable) через идемпотентную мини-миграцию
`_ensure_job_columns` — alembic в проекте нет. Без этой колонки перезапуск
«Точного переноса» молча превратился бы в обычную ИИ-сборку: пользователь просит
повторить то же самое и получает другое. Худший вид бага — тихий.

У старых строк `NULL` = `False`, что верно: до появления флага все сборки были обычными.

## 2. Плашка доступности моделей

### Что было

Инцидент 2026-08-04 (см. `2026-08-04-model-fallback.md`) научил систему быстро
отказывать, но узнаёт об отказе пользователь всё равно постфактум — потратив
загрузку файла и место в очереди. Состояние провайдера видно только серверу.

### Решение

`GET /api/models/health` → `{"state": "ok|fallback|down|unknown", "primary_up": bool,
"fallback_up": bool|null, "checked_ago_sec": int|null}`.

- **Имена моделей наружу не отдаём** — только роли («основная» / «резервная»).
  Согласуется с правилом соседнего эндпоинта `/internal/stats`: наружу уходит
  перечисление, а не внутренности.
- Кэш в памяти процесса, **TTL 60 с, stale-while-revalidate**: ответ мгновенный по
  последнему известному состоянию, а если данным больше TTL — фоном стартует новая
  проба. Флаг «проба в полёте» гарантирует одну пробу на все вкладки.
- Холодный старт → `state: "unknown"`, UI показывает нейтральное «проверяю…» и
  перезапрашивает через 3 с (не более 3 раз — без ключа API состояние останется
  `unknown` навсегда, и бесконечный поллинг был бы бессмысленным).
- Резерв не настроен (`CLOUDRU_FALLBACK_MODEL=""`) → `fallback_up: null`, второй
  индикатор скрыт.

### Развилка: чем мерить

- ❌ **Свой health-модуль с собственным HTTP** — продублирует знание о провайдере
  (base_url, ключ, имена моделей) и со временем разъедется с движком.
- ❌ **`KimiClient.preflight()`** — он **липко переключает** клиент на резерв. Для
  плашки нужна read-only проверка; побочный эффект тут недопустим.
- ✅ **`KimiClient.probe(model)`** — бывший приватный `_probe`, открыт вместе со
  свойством `fallback_model`. Состояние клиента не меняется, знание о провайдере
  одно на всех.

Обе модели пробуются параллельно (`asyncio.gather` поверх `to_thread`, пробы
синхронные): худший случай — один `PROBE_TIMEOUT`, а не два подряд.

### UI

Компактная строка над кнопкой «Создать», два индикатора «Основная модель» /
«Резервная» + строка «проверено N назад» (живой таймер, тикает раз в секунду).

| state | тон | текст |
|---|---|---|
| `ok` | зелёный | Сервис ИИ работает штатно |
| `fallback` | жёлтый | Основная модель не отвечает. Соберём на резервной — может быть медленнее |
| `down` | красный | Сервис ИИ недоступен: не отвечают обе модели. Сборка сейчас не пройдёт |
| `unknown` | нейтральный | Проверяю доступность сервиса ИИ… |

При `down` кнопка «Создать» **остаётся активной**: состояние могло измениться за
секунды, а запрет запуска был бы решением за пользователя на основании данных
минутной давности. Клик показывает предупреждение в `#result` с кнопкой «Всё равно
запустить».

Обновление — при загрузке страницы и при возврате во вкладку (`visibilitychange`),
если данным больше 60 с. Фонового поллинга нет: простаивающий сервис не должен
жечь токены. Отсюда и таймер — он честно показывает, насколько свежие данные.

## Не делаем

- **Не перезапускаем успешные сборки** (`done`) — у них есть «Открыть»; «собрать
  ещё раз то же самое» — другая фича с другим смыслом.
- **Не блокируем кнопку «Создать»** при `down` (см. выше).
- **Не поллим health в фоне** — состояние нужно ровно в момент, когда пользователь
  смотрит на страницу.
- **Не показываем имена моделей** пользователю: роль стабильна, имя — деталь
  реализации, которая менялась уже дважды (Kimi → MiniMax → …).
